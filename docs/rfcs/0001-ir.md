# RFC 0001 — `dol-ir` design (noun/verb hybrid, ACL, Target, schema catalog)

- Status: **Accepted**
- Authors: DOL maintainers

## Summary

`dol-ir` is a backend-agnostic intermediate representation built around a
single `Operation` enum addressed by a universal `Target`. Schemas are
referenced through a catalog rather than embedded inline. Storage and
file operations collapse onto the same data verbs (`Insert`, `Update`,
`Replace`, `Delete`, `Query`, `Probe`, `Describe`) by varying
`TargetKind`. Access control is generalised from SQL DCL to a
cross-system **ACL** category covering relational stores, object stores,
file trees, KV stores, message queues, streams, and APIs.

## Motivation

A useful IR for DOL has to satisfy four constraints simultaneously:

- **Growable structural surface.** `Schema`, `Field`, `Index`, `Lookup`,
  `Policy`, `Mask`, `Quota`, `Audit` are all structural / governance
  concerns. Encoding them as `Verb + Noun` triples (`DefineLookup`,
  `DropLookup`, `AlterLookup`, …) is combinatorial.
- **Backend-neutral data verbs.** `PutObject`, `GetObject`,
  `ListObjects`, `ReadFile`, `WriteFile`, and `MoveFile` are the same
  verbs as `Insert`, `Update`, `Replace`, and `Query` — only the target
  changes.
- **Schemas as data, not types.** Passing schemas inline couples the IR
  to a specific Rust type wall and makes referencing a program against
  an external catalog awkward.
- **Cross-system access control.** SQL "DCL" is a vocabulary, not a
  shape. Object stores, KV, message queues, filesystems, and APIs all
  have access control with the same shape.

## Guide-level explanation

Every DOL program is a sequence of `Operation`s.

Each `Operation` is one of:

1. **Structural / governance — variant is a noun**: `Schema`, `Field`,
   `Index`, `Lookup`, `Policy`, `Mask`, `Quota`, `Audit`. These payloads
   share a common `StructuralVerb` (`Create`, `Drop`, `Alter`, `Rename`,
   `Truncate`).
2. **Data / query / authorization — variant is a verb**: `Insert`,
   `Update`, `Replace`, `Delete`, `Upsert`, `Append`, `Query`, `Probe`,
   `Describe`, `Grant`, `Revoke`.
3. **Meta**: `Tx`, `Extension`, `Raw` (feature-gated).

`Update` is partial modification (SET / PATCH-like). `Replace` is full
overwrite (PUT / `replaceOne` / object replacement). There is no
separate `Patch` variant — having both `Update` and `Patch` is
semantically redundant.

Every operation applies to a `Target`:

```rust
pub struct Target {
    pub kind: TargetKind,
    pub locator: Locator,
    pub alias: Option<Symbol>,
    pub schema: SchemaBinding,
}

pub enum TargetKind {
    Relation,
    Document,
    KeyValue,
    Blob,
    FileTree,
    ApiResource,
    StreamTopic,
    Virtual,
    Custom(Symbol),
}

pub enum SchemaBinding {
    Declared(SchemaRef),
    Inferred,
    Opaque,
}
```

`Locator` is structured data, not a string:

```rust
pub struct Locator {
    pub namespace: Option<Symbol>,
    pub name: Symbol,
    pub path: SmallVec<[Symbol; 2]>,
}
```

`path` covers nested document paths, S3 key segments, file-tree
segments, and topic partitions. `Symbol` is an interned `u32` handle
into `dol_expr::Interner`, so addressing has no per-operation
allocations and equality is cheap.

### Schemas live in a catalog

```rust
pub struct SchemaRef { catalog: CatalogId, schema: SchemaId }

pub struct Program {
    pub operations: Vec<Operation>,
    pub expr_arena: ExprArena,
    pub interner: Interner,
    pub schema_catalog: Option<SchemaCatalog>,
}
```

Operations carry a `SchemaRef` rather than embedding the schema body.
This turns schemas into addressable data and decouples the IR from any
one Rust type.

### Categories and ACL

```rust
pub enum Category { DDL, DML, DQL, ACL, Tx, Other }
```

`ACL` replaces `DCL`. Lifecycle objects (`Policy`, `Mask`, `Quota`,
`Audit`) are nouns; lifecycle actions (`Grant`, `Revoke`) are verbs.
The category name applies cleanly to filesystems, object stores, IAM,
message queues, KV stores, APIs, and streams as well as databases.

### Storage and file operations

There is no dedicated `PutObject` / `GetObject` / `ListObjects` /
`ReadFile` / `WriteFile` / `MoveFile` variant. The standard verbs map
onto `TargetKind::Blob` and `TargetKind::FileTree`:

| Storage verb        | IR `Operation` |
| ---                 | --- |
| Put object          | `Insert` against `TargetKind::Blob` |
| Get object          | `Query` against `TargetKind::Blob` |
| List objects        | `Query` (or `Probe`) against `TargetKind::Blob` |
| Read file           | `Query` against `TargetKind::FileTree` |
| Write file (full)   | `Replace` against `TargetKind::FileTree` |
| Move / rename file  | `Update` against `TargetKind::FileTree` |
| Delete file         | `Delete` against `TargetKind::FileTree` |

### Capabilities

The fast `u64` `BackendCapabilities` bitset is retained for the hot
path, plus an open `CapabilityTag` / `CapabilitySet` vocabulary for
forward compatibility (e.g. `OPAQUE_SCHEMA`, `BLOB_TARGETS`,
`FILE_TREE_TARGETS`, `STREAM_TARGETS`, `REPLACE_OP`, `PROBE_OP`,
`DESCRIBE_OP`, `MULTI_STATEMENT_TX`, `RAW_PASSTHROUGH`). `dol-check`
produces uniform diagnostics from `CapabilityCheck { op, target, verb }`
triples — e.g. *"backend `pg` does not support `Append` on
`TargetKind::StreamTopic`"*.

### Transactions

`Tx` is a meta-operation, not DDL/DML/DQL/ACL:

```rust
pub enum TxOp {
    Begin(TxBegin),
    Commit,
    Rollback,
    Savepoint(Symbol),
    ReleaseSavepoint(Symbol),
    RollbackTo(Symbol),
    Atomic { ops: Vec<Operation>, opts: TxOptions },
}
```

`TxOptions` covers `isolation`, `read_only`, and `label` and is shared
between `TxBegin` and `Atomic`.

### Expression slots

Every default / check / generated / using / check-policy /
object-source-from-expr expression is `Option<NodeId>` into the
program's `ExprArena`. There are no `String`-typed expression fields in
any `Operation` payload.

## Reference-level explanation

### Outer enum

```rust
pub enum Operation {
    // structural / management — variant = noun
    Schema(Box<SchemaOp>),
    Field(Box<FieldOp>),
    Index(Box<IndexOp>),
    Lookup(Box<LookupOp>),

    // ACL / governance — variant = noun
    Policy(Box<PolicyOp>),
    Mask(Box<MaskOp>),
    Quota(Box<QuotaOp>),
    Audit(Box<AuditOp>),

    // DML — variant = verb
    Insert(Box<Insert>),
    Update(Box<Update>),
    Replace(Box<Replace>),
    Delete(Box<Delete>),
    Upsert(Box<Upsert>),
    Append(Box<Append>),

    // DQL — variant = verb
    Query(Box<Query>),
    Probe(Box<Probe>),
    Describe(Box<Describe>),

    // ACL actions — variant = verb
    Grant(Box<Grant>),
    Revoke(Box<Revoke>),

    // meta
    Tx(Box<TxOp>),
    Extension(Box<OperationExtension>),
    Raw(Box<RawOp>), // feature = "raw"
}
```

### Module layout

Operation payloads are grouped under `lib/ir/src/operation/` by
category, mirroring the noun/verb groups above:

```
operation/
├── mod.rs          — Operation enum, From impls, size assertion
├── kind.rs         — OpKind, Category, required_capabilities
├── shared/         — StructuralVerb (used by every noun module)
├── ddl/            — schema, field, index, lookup
├── dml/            — insert, update, replace, delete, upsert, append
├── dql/            — query, probe, describe
├── acl/            — grant, revoke, policy, mask, quota, audit
├── tx.rs
└── meta/           — extension, raw (feature-gated)
```

Flat re-exports (`dol_ir::operation::Insert`, etc.) remain so existing
imports and `dol_ir::prelude::*` keep working. New code can also import
from the per-category modules:
`use dol_ir::operation::dml::Insert;`.

### Static invariants

- `size_of::<Operation>() ≤ 64` — `const _: () = assert!(...)` plus
  `xtask size`.
- `Operation: Send + Sync + 'static` — static assertion.
- `#![deny(unsafe_code)]` retained.
- Every payload derives `Debug, Clone, PartialEq` and is
  `Serialize`/`Deserialize` under the `serde` feature.
- No `String`-typed expression slot anywhere in `Operation` payloads.

### Wire format

Persistent serialisation lives in [`dol-wire`](../../lib/wire), which
carries its own header / framing version independent of the in-memory
IR. The IR itself does not embed a "schema version" envelope; the
wire layer is the source of truth for evolution.

### Backend trait

```rust
pub trait Backend {
    type Output;
    fn compile(&self, program: ProgramRef<'_>) -> Result<Self::Output, BackendError>;
}

impl<'a> From<&'a Program> for ProgramRef<'a> { /* ... */ }
```

`BackendError` is `#[non_exhaustive]` and carries a
`dol_core::Diagnostic` plus optional `Span`, so kinds like `Capability`,
`Extension`, and `AclDenied` can be added without breakage. `compile`
stays sync; an async `Backend` is a follow-up RFC.

### `Raw` is feature-gated

```rust
#[cfg(feature = "raw")]
pub struct RawOp {
    pub dialect: Option<Symbol>,
    pub body: String,
    pub params: SmallVec<[NodeId; 4]>,
}
```

Use of `Raw` adds the `RAW_PASSTHROUGH` capability tag.

## Acceptance criteria

- `size_of::<Operation>() ≤ 64`.
- Serde round-trips every variant.
- Every `TargetKind` has DDL, DML, DQL, ACL test fixtures where the
  kind supports them.
- `dol-check` emits capability-tag and privilege diagnostics.
- Docs explain the noun-vs-verb variant rule (`docs/IR.md`).

## Non-goals

- No new backend implementations.
- No changes to `dol-expr` arena/interner internals.
- No async `Backend` trait.
- No removal of `Symbol`-equivalent types from `dol-core` / `dol-expr`;
  the IR adopts whichever already exists.

## Drawbacks

- The noun/verb asymmetry needs to be taught: structural operations
  vary primarily by *object family*, while data/query/auth actions vary
  primarily by *verb*. `docs/IR.md` states the rule explicitly.

## Alternatives considered

- **All-noun** (`Schema`, `Index`, `Row`, `Document`, `Object`, …):
  collapses every verb into a payload field. Rejected because dispatch
  on the hot path becomes a two-level match for every DML/DQL operation.
- **All-verb** (`Create`, `Drop`, `Alter`, `Insert`, `Update`, …):
  forces the `Create` arm to fan out into per-object-family sub-enums.
  Rejected because it inverts the asymmetry: structural code is the
  consumer that benefits most from variant-as-noun.
- **Keep `Patch` alongside `Update`**: rejected as semantically
  redundant. The `Update` (partial) vs. `Replace` (full) split covers
  the same ground without ambiguity.
