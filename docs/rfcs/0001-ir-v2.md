# RFC 0001 — `dol-ir` v2 (noun/verb hybrid, ACL, Target, schema catalog)

- Status: **Accepted**
- Authors: DOL maintainers
- Tracking PR sequence: see "Sequencing" below.

## Summary

Rework `dol-ir` from the closed `Statement` enum into a backend-agnostic
`Operation` model addressed by a universal `Target`, with schemas referenced
through a catalog rather than embedded inline. Storage and file operations
collapse onto the same data verbs (`Insert`, `Update`, `Replace`, `Delete`,
`Query`, `Probe`, `Describe`) by varying `TargetKind`. Access control is
generalised from SQL DCL to a cross-system **ACL** category. Compatibility with
existing `Statement` consumers is preserved through a `compat::statement` shim
and a `From<Statement> for Operation` conversion until downstream crates have
migrated.

## Motivation

The current `Statement` enum mixes concerns:

- DDL nouns (`DefineEntity`, `AlterEntity`, `DropEntity`, `DefineLookup`,
  `DefineType`, `DefinePolicy`) are spelt as `Verb + Noun` triples, which makes
  growing the structural surface (e.g. adding `Index`, `Quota`, `Mask`, `Audit`)
  combinatorial.
- Storage and file ops (`PutObject`, `GetObject`, `ListObjects`, `ReadFile`,
  `WriteFile`, `MoveFile`) duplicate DML semantics already expressed by
  `Insert`, `Update`, `Replace`, and `Query`, just against different targets.
- Schemas are passed inline, which couples the IR to a specific Rust type wall
  and makes serialising or referencing a program against an external catalog
  awkward.
- "DCL" is a SQL-specific framing. Object stores, KV, message queues,
  filesystems, and APIs all have access control with the same shape but
  different vocabulary.
- There is no formal `Target` primitive, so each variant re-encodes addressing
  ad hoc.

## Guide-level explanation

Every DOL program is a sequence of `Operation`s.

Each `Operation` is one of:

1. **Structural / governance — variant is a noun**: `Schema`, `Field`, `Index`,
   `Lookup`, `Policy`, `Mask`, `Quota`, `Audit`. These payloads share a common
   `StructuralVerb` (`Create`, `Drop`, `Alter`, `Rename`, `Truncate`).
2. **Data / query / authorization — variant is a verb**: `Insert`, `Update`,
   `Replace`, `Delete`, `Upsert`, `Append`, `Query`, `Probe`, `Describe`,
   `Grant`, `Revoke`.
3. **Meta**: `Tx`, `Extension`, `Raw` (feature-gated).

`Update` is partial modification (SET / PATCH-like). `Replace` is full overwrite
(PUT / `replaceOne` / object replacement). `Patch` is dropped from the IR —
having both `Update` and `Patch` is semantically redundant.

Every operation applies to a `Target`:

```rust
pub struct Target {
    pub kind: TargetKind,
    pub locator: Locator,
    pub alias: Option<Symbol>,
    pub schema: SchemaBinding,
}

pub enum TargetKind {
    Relation,
    Document,
    KeyValue,
    Blob,
    FileTree,
    ApiResource,
    StreamTopic,
    Virtual,
    Custom(Symbol),
}

pub enum SchemaBinding {
    Declared(SchemaRef),
    Inferred,
    Opaque,
}
```

`Locator` is structured data, not a string:

```rust
pub struct Locator {
    pub namespace: Option<Symbol>,
    pub name: Symbol,
    pub path: SmallVec<[Symbol; 2]>,
}
```

`path` covers nested document paths, S3 key segments, file-tree segments, and
topic partitions. `Symbol` is an interned `u32` handle into
`dol_expr::Interner`, so addressing has no per-operation allocations and
equality is cheap.

### Schemas live in a catalog

```rust
pub struct SchemaRef { catalog: CatalogId, schema: SchemaId }

pub struct Program {
    pub operations: Vec<Operation>,
    pub expr_arena: ExprArena,
    pub interner: Interner,
    pub schema_catalog: Option<SchemaCatalog>,
}
```

Operations carry a `SchemaRef` rather than embedding the schema body. This
turns schemas into addressable data and decouples the IR from any one Rust
type.

### Categories and ACL

```rust
pub enum Category { DDL, DML, DQL, ACL, Tx, Other }
```

`ACL` replaces `DCL`. Lifecycle objects (`Policy`, `Mask`, `Quota`, `Audit`)
are nouns; lifecycle actions (`Grant`, `Revoke`) are verbs. The category name
applies cleanly to filesystems, object stores, IAM, message queues, KV stores,
APIs, and streams as well as databases.

### Storage and file operations

`PutObject`, `GetObject`, `ListObjects`, `ReadFile`, `WriteFile`, `MoveFile`
disappear as distinct variants. The compat shim maps them to the standard
verbs against `TargetKind::Blob` or `TargetKind::FileTree`:

| v1 `Statement` | v2 `Operation` |
| --- | --- |
| `PutObject`   | `Insert` against `TargetKind::Blob` |
| `GetObject`   | `Query` against `TargetKind::Blob` |
| `ListObjects` | `Query` (or `Probe`) against `TargetKind::Blob` |
| `ReadFile`    | `Query` against `TargetKind::FileTree` |
| `WriteFile`   | `Replace` against `TargetKind::FileTree` |
| `MoveFile`    | `Update` against `TargetKind::FileTree` |

### Capabilities

The fast `u64` `BackendCapabilities` bitset is retained for the hot path, plus
an open `CapabilityTag` / `CapabilitySet` vocabulary for forward compatibility
(e.g. `OPAQUE_SCHEMA`, `BLOB_TARGETS`, `FILE_TREE_TARGETS`, `STREAM_TARGETS`,
`REPLACE_OP`, `PROBE_OP`, `DESCRIBE_OP`, `MULTI_STATEMENT_TX`,
`RAW_PASSTHROUGH`). `dol-check` produces uniform diagnostics from
`CapabilityCheck { op, target, verb }` triples, e.g. *"backend `pg` does not
support `Append` on `TargetKind::StreamTopic`"*.

### Transactions

`Tx` is a meta-operation, not DDL/DML/DQL/ACL:

```rust
pub enum TxOp {
    Begin(TxBegin),
    Commit,
    Rollback,
    Savepoint(Symbol),
    ReleaseSavepoint(Symbol),
    RollbackTo(Symbol),
    Atomic { ops: Vec<Operation>, opts: TxOptions },
}
```

`TxOptions` covers `isolation`, `read_only`, and `label` and is shared between
`TxBegin` and `Atomic`.

### Expression slots

Every place the v1 IR uses `Option<String>` for a default / check / generated /
using / check-policy / object-source-from-expr expression becomes
`Option<NodeId>` into the program's `ExprArena`. Any `String` expression slot
in an `Operation` payload is a bug.

## Reference-level explanation

### Outer enum

```rust
pub enum Operation {
    // structural / management — variant = noun
    Schema(Box<SchemaOp>),
    Field(Box<FieldOp>),
    Index(Box<IndexOp>),
    Lookup(Box<LookupOp>),

    // ACL / governance — variant = noun
    Policy(Box<PolicyOp>),
    Mask(Box<MaskOp>),
    Quota(Box<QuotaOp>),
    Audit(Box<AuditOp>),

    // DML — variant = verb
    Insert(Box<Insert>),
    Update(Box<Update>),
    Replace(Box<Replace>),
    Delete(Box<Delete>),
    Upsert(Box<Upsert>),
    Append(Box<Append>),

    // DQL — variant = verb
    Query(Box<Query>),
    Probe(Box<Probe>),
    Describe(Box<Describe>),

    // ACL actions — variant = verb
    Grant(Box<Grant>),
    Revoke(Box<Revoke>),

    // meta
    Tx(Box<TxOp>),
    Extension(Box<OperationExtension>),
    Raw(Box<RawOp>), // feature = "raw"
}
```

### Static invariants

- `size_of::<Operation>() ≤ 64` — `static_assertions::const_assert!` plus
  `xtask size`.
- `Operation: Send + Sync + 'static` — static assertion.
- `#![deny(unsafe_code)]` retained.
- Every payload derives `Debug, Clone, PartialEq` and is
  `Serialize`/`Deserialize` under the `serde` feature.
- No `String`-typed expression slot anywhere in `Operation` payloads.

### Versioned wire format

```rust
pub const IR_SCHEMA_VERSION: u32 = 2;
```

`Program` serialises through a `{ version, body }` envelope. v1 (current
`Statement`-based) is decoded via `compat::statement` into `Operation`, then
re-emitted as v2.

### Backend trait

```rust
pub trait Backend {
    type Output;
    fn compile(&self, program: ProgramRef<'_>) -> Result<Self::Output, BackendError>;
}

impl<'a> From<&'a Program> for ProgramRef<'a> { /* ... */ }
```

`BackendError` becomes `#[non_exhaustive]` and carries a `dol_core::Diagnostic`
plus optional `Span`, so kinds like `Capability`, `Extension`, and `AclDenied`
can be added without breakage. `compile` stays sync; an async `Backend` is a
follow-up RFC.

### `Raw` is feature-gated and parameterised

```rust
#[cfg(feature = "raw")]
pub struct RawOp {
    pub dialect: Option<Symbol>,
    pub body: String,
    pub params: SmallVec<[NodeId; 4]>,
}
```

Use of `Raw` adds the `RAW_PASSTHROUGH` capability tag.

## Acceptance criteria

- `size_of::<Operation>() ≤ 64`.
- `Statement` compatibility remains for the duration of the migration.
- Every old `Statement` variant maps to `Operation`.
- Serde round-trips all new variants.
- v1 → v2 decode works through the compat layer.
- Every `TargetKind` has DDL, DML, DQL, ACL test fixtures where the kind
  supports them.
- `dol-check` emits capability-tag and privilege diagnostics.
- Docs explain the noun-vs-verb variant rule.
- `MIGRATION.md` maps old APIs to new APIs (schema definition, alter, query,
  upsert, policy, grant, transaction, file write, object put, …).
- Every entry in the "v1 → v2" table has a corresponding test in
  `lib/ir/tests/compat_v1_to_v2.rs`.

## Non-goals

- No new backend implementations land in this rework.
- No changes to `dol-expr` arena/interner internals.
- No async `Backend` trait.
- No wire-format changes in `dol-wire` beyond honouring `IR_SCHEMA_VERSION`.
- No removal of `Symbol`-equivalent types from `dol-core`/`dol-expr`; we adopt
  or alias whichever already exists.

## Drawbacks

- Two parallel surfaces (`Statement` and `Operation`) during the migration
  window cost reviewer attention. The compat shim mitigates this by ensuring
  callers can move at their own pace.
- The noun/verb asymmetry needs to be taught: structural operations vary
  primarily by *object family*, while data/query/auth actions vary primarily by
  *verb*. `docs/IR.md` will state the rule explicitly.

## Alternatives considered

- **All-noun** (`Schema`, `Index`, `Row`, `Document`, `Object`, …): collapses
  every verb into a payload field. Rejected because dispatch on the hot path
  becomes a two-level match for every DML/DQL operation.
- **All-verb** (`Create`, `Drop`, `Alter`, `Insert`, `Update`, …): forces the
  `Create` arm to fan out into per-object-family sub-enums. Rejected because
  it inverts the asymmetry: structural code is the consumer that benefits most
  from variant-as-noun.
- **Keep `Patch` alongside `Update`**: rejected as semantically redundant. The
  `Update` (partial) vs. `Replace` (full) split covers the same ground without
  ambiguity.
